# 派活通用规矩（所有模板都先读这一份）

接活的一方（Codex / Cursor / 别的 Claude 会话 / 子代理）照这份做。每个具体模板只写「这一类活多出来的要求」。
**复制到项目后，把带 ★ 的几处改成你项目的。**

## 一 语言与产物

- 交回的文字用派活方的语言、大白话；代码标识符、路径、命令保持原文。
- ★ 产物放哪：`<项目>/out/<卡号>/…`（报告）、`<项目>/scratch/<卡号>/`（一次性脚本）。别写进系统临时目录（会被清）。
- 没有版本控制的目录里，覆盖别人的文件前先留副本（`<名>.bak-<日期>`）。

## 二 绝对不许碰

- ★ 生产 / 测试服务器：不部署、不重启、不跑会改数据的脚本。要上测试服的活由派活方排总线锁（`lock take`）自己做。
- ★ 主干分支：不 commit / push / merge / rebase / reset；别人的分支一律不动。
- 派活方正在用的工作目录：别在里面切分支、改文件。要读代码用 `git show <分支>:<路径>`，或自己建 worktree，用完删掉。
- ★ 共享配置和大家都改的文件（路由表、总配置、进度文档）：除非派活明写，否则不改。

## 三 证据口径（调研类必守）

每条结论标一个证据档，写上出处：

| 标签 | 含义 | 出处写法 |
|---|---|---|
| 【实证】 | 源码 / 数据表 / 官方文档原文 | `<路径>:<行>` 或 URL |
| 【实测】 | 自己跑出来的（脚本、命令、计数） | 脚本路径 + 命令 + 结果 |
| 【推测】 | 推理，没有直接证据 | 写推理链 |
| 【没找到】 | 查过、没有 | **写清楚查了哪里、用的什么命令** |

- **别把原文的形状降级成省事的形状**：原文写「找来 X、第 N 次、剩余 M 分钟」，就照原文定口径；想简化就写成「开放问题」交给人定。
- **「没有 X」要自己 grep 过再写**，把命令和结果贴进报告。
- 自己测试环境上看到的现象不是官方证据，最多算【实测】。

## 四 git 与提交（实现类才有）

- 只在派活给的分支、自己的 worktree 里干活。
- 提交说明写清「改了什么、为什么」；只 `git add` 自己改的文件。
- ★ 测试以哪条命令为准：`<项目的测试命令>`。

## 五 交活

- 做完：`python <总线>/bus.py done <任务号> "一句话结论 + 产物路径 + 开放问题几条"`。
- 做不成 / 要越界 / 要人拍板：`done <任务号> --fail "卡在哪、需要谁定什么"`，别硬做。
- 交回的文字里不贴大段原文；给路径和行号，派活方会自己去看。
