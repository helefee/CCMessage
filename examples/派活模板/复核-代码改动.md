# 模板：交叉复核一段代码改动（第二双眼睛）

先读 `00-通用规矩.md`。这是「换个模型再看一遍」，**不替代**派活方自己的正式代码审查。
Claude 写的交给 Codex / Cursor 复核，反过来也一样（同一个模型复核自己没用）。

## 派活时填的参数

- **分支 / 提交范围**：`<基点>..<头>`
- **计划 / 规格**：路径
- **重点看哪里**（可选）：派活方自己不放心的几处
- **不用看的**：生成物、别人的未跟踪文件

## 要做的事

1. **别动派活方的工作树**：自己建只读 worktree（`git worktree add --detach <目录> <头提交>`），看完删掉。
2. 对照计划逐条看：计划要求的做到没有、做了计划没要求的没有。
3. 找真问题，按这个顺序：
   - 会让程序崩 / 卡住 / 丢数据的；
   - 行为错的（和规格 / 原文口径不一致；边界：断线重连、中途取消、并发、权限）；
   - 并发与时序（异步回来状态变了、同一份数据被两处写）；
   - 测试没钉住的分支（只钉了结果没钉调用路径、判据恒真、桩和真函数不同形）；
   - 老功能被连带改坏（改了共享函数的签名 / 返回值，别的调用方没跟上）。
4. **每条问题自己验证一遍再报**：能写最小复现就写；只是怀疑的标「待核」。别报风格偏好。

## 交回什么

`<交回目录>/review-<模型>.md`：

```
# 交叉复核（<模型>，<日期>，看的是 <基点>..<头>）
| # | 严重度（崩 / 错 / 漏测 / 小） | 文件:行 | 问题 | 怎么触发 | 建议 | 验证（复现命令或「待核」） |
## 计划对照（逐条：做到 / 没做到 / 多做了）
## 看过没问题的地方（一句一条，让派活方知道覆盖面）
```

交活消息：几条「崩」、几条「错」、报告路径。没问题就说没问题，不要凑数。
